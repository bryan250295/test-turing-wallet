1. 执行摘要

Learning Bridge 把 TBC Testnet 上的 legacy FT 以 1:1 方式映射成 HyperEVM Testnet ERC-20。正向时，用户把源 FT 转入每订单独立的 TBC custody 地址；后端验证资产身份、完整输入祖先、UTXO、规范区块和至少 6 次确认；V1.5 Minter 随后在 HyperEVM mint 对应 wrapped token。反向时，wrapped token 被永久锁入不可提取的 escrow，后端确认锁仓后使用 TBC custody reserve 构建并签署源 FT 返还交易。

1:1

源 FT raw amount 与 wrapped ERC-20 raw amount固定对应。

6 + 6

TBC 和 HyperEVM 关键交易均要求 6 次确认。

2-of-2

Admin 高权限动作必须由两名 signer 共同批准。

关键设计结论

  1. 低 gas 来自把 TBC 共识证明移出 EVM。每笔 mint 只执行固定 ABI 的 ERC-20 mint 与 replay protection，不在链上跑 header/PoW/DAA/Merkle 验证。
  2. Admin 与 Minter 分离。Admin multisig 只负责 pause/unpause、轮换 minter 等低频治理；Minter 只负责高频 mint，不能更改 Admin。
  3. 后端不保存 MetaMask 私钥。报价、calldata、nonce 和 gas budget 由后端准备并验证；最终 EVM 发送必须由对应 MetaMask 账户确认。
  4. TBC custody key 存于 Compose secret。它用于 custody 地址恢复和反向源链签名，是 V1.5 的主要托管风险之一。
  5. 自动化只观察，不擅自签名。后台每约 60 秒检查 TBC，每约 12 秒检查已提交的 HyperEVM transaction；自动刷新不会生成新的资金交易。
  6. 重复发送保护优先。订单、付款 attempt、outpoint、EVM nonce、orderId/depositId 与 redemptionId 都有数据库或合约级唯一约束。
当前主路线

V1.5 支持从 Turing Wallet 动态读取当前 TBC FT，逐 token 建立独立 wrapped route。每个 source token 不共享 ERC-20、reserve accounting 或 replay namespace。

生产前缺口

需要第三方审计、密钥隔离/HSM、正式监控与告警、灾难恢复演练、限额与人工审批策略、API 多源交叉验证，以及对 Minter/custody compromise 的应急预案。

V1.5 服务分工

正向

  • BridgeAssetVerifier：FT genesis/metadata/canonical chain
  • BridgeCustodyService：每订单 custody key 加密
  • BridgeDepositVerifier：付款输出、祖先、脚本与 UTXO
  • BridgeCallVerifier：unpause/mint receipt 与 event
  • BridgeAutomationService：观察确认数

反向

  • RedemptionEscrowVerifier：escrow runtime/binding/owner
  • RedemptionWalletService：approve/reset/lock wallet call
  • RedemptionLockVerifier：永久锁事件
  • RedemptionReleaseEngine：TBC fee、unsigned release、签名/广播
  • BridgeV15MultisigService：2-of-2 activation

并发与失败原则

  • 按 identity、sender、order 或 redemption 使用 advisory/application locks，避免并发 nonce 和重复 reserve。
  • 外部 read 有限重试；钱包 send、签名与 broadcast 不自动重试。
  • 超时/上游 unavailable 保留已保存证据；错误不等同于“交易未发送”。
  • 所有 API JSON response 采用 { data } 或标准化错误，附 X-Request-Id。

8. Solidity 合约设计

BridgeWrappedFT

特性实现
绑定immutable sourceContractId、sourceDecimals、chain 998。
初始状态paused = true、totalSupply = 0，必须经 Admin 2-of-2 activation。
MintmintFromDeposit(orderId, sourceContractId, sourceTxid, vout, recipient, amountRaw)，仅 minter、仅 whenNotPaused。
ReplayprocessedOrders 与由 domain/FT/txid/vout 生成的 processedDeposits 双重防重。
治理owner 可 pause/unpause/setMinter；Ownable2Step；禁止 renounceOwnership。

BridgeAdminMultisig

特性实现
成员两个 immutable signer，必须不同且非零；固定 threshold=2。
提案保存 target + calldata；proposer 自动获得第一票；nonce 防 actionId 重用。
执行另一 signer 批准时原子执行；失败整体 revert；同 signer 不能重复批准。
权限合约本身不持有 mint role；仅作为 wrapped/escrow owner。

LearningRedemptionEscrow

特性实现
永久锁lockForRedemption 用 SafeERC20 transferFrom；没有 withdraw/rescue/upgrade/forward。
绑定immutable wrapped token、sourceContractId、decimals、chain 998。
精确金额比较 escrow balance before/after；防 fee-on-transfer 异常。
ReplayprocessedRedemptions；event 绑定 holder、recipient hash、amount。
经济含义锁仓不是 burn；wrapped totalSupply 不变，但被锁 token 永久不可流通。
链间事实不在 Solidity 内验证

三个 V1.5 合约都不读取或验证 TBC header、PoW、DAA、Merkle proof、UTXO set。TBC 事实检查属于后端信任边界，这正是其 gas 接近 V1 的原因。

9.1 正向桥：调用链与恢复

前端 → 后端 → 钱包调用

BridgeOrdersPOST order；只传 deploymentId、idempotencyKey、amount、recipient
→
BridgeOrdersService从 session 决定 sender；从 verified deployment 决定 token/chain/contract；在事务内分配 custody
→
BridgeSourcePaymentpayment/begin → Turing Wallet FT_TRANSFER → payment/submit(txid)
→
BridgeAutomationService观察 TXID；DepositVerifier 形成 BridgeDeposit；ProgressService 发布 SSE invalidation
→
BridgeSettlementquote → begin → MetaMask send → submit hash → receipt check → completed

为什么使用 begin / submit / check 三段式

阶段保存内容解决的问题
quote/prepare条款、calldata、nonce、gas、有效期用户先审阅；后端固定交易意图
beginawaiting_wallet slot刷新/双击不会再次弹出新钱包交易
submit公开 TXID / txHash后端重启后仍可继续观察
checkreceipt、block、confirmations、actual fee不信任钱包“已发送”提示

故障恢复分支

钱包已发，但 API submit 失败

从 Turing Wallet history 或 MetaMask Activity 取原 hash，使用 recovery 输入保存；绝不再次付款。

钱包 prompt 被拒绝

确认 Activity 没有链上 transaction，再执行 cancel/notSent 清除 awaiting_wallet；cancel 不能取消已广播交易。

RPC/API unavailable

保留当前记录与 hash，稍后 check；有限重试仅适用于安全的 public read。

确认数不足

后台 observer 继续读取，不需重新付款；页面通过 SSE/手动 refresh 更新。

前端 TXID 自动化

正向 FT payment 的 token、amount 与 custody address 自动传入 Turing Wallet；成功返回 TXID 后自动保存。用户仍需在钱包中确认，因为网页没有也不应拥有 TBC 私钥。

Custody 加密

主密钥经 HKDF-SHA256 按 order UUID 派生 AES-256 key；每条记录使用随机 12-byte IV、16-byte GCM tag，AAD 绑定版本、网络、identity、order、termsHash、address 和 public key。数据库保存密文与 key fingerprint，不保存明文 WIF。

为什么 bridge 状态不是全部 WebSocket

  • WebSocket 用于完整、持续的交易历史 snapshot；bridge settlement 只需要“状态可能变化”的轻量通知，因此采用 SSE。

为什么 V1.5 gas 低

V1.5 每笔 mint

固定 calldata、replay mappings、ERC-20 balance/supply 更新、event。TBC 证明在后端检查。

V3 proof mint

header relay、PoW、DAA、Merkle branch、bounded legacy FT ancestors/signatures 等在 EVM 验证，calldata 与 computation 都显著增加。

费用控制

  • 后端用 eth_estimateGas + 当前 gas price，gas units 增加 20% buffer；报价通常 60 秒失效。
  • 用户审阅的是最大 budget，最终 actual fee 由 receipt 的 gasUsed × effectiveGasPrice 记录。
  • Admin 动作不进入每笔 transfer；仅部署、激活、pause 或 rotate minter 时使用两笔 multisig gas。
  • 不能通过降低 gasLimit 绕过实际执行成本；过低只会导致 out-of-gas。真正降低成本的选择是减少链上验证工作或选择更低 gas price 时段。
成本与信任交换

V1.5 接近 V1 的费用并非“同等 trustless security 下的优化”，而是把共识证明换成 operator/backend trust。文档与 UI 必须持续清楚表达这一点。

15. 安全模型与威胁分析

威胁现有控制剩余风险/建议
单一 Admin 私钥泄漏2-of-2 multisig；exact calldata；signers 与 minter 分离若两 signer 同设备/seed，隔离无效；应使用不同硬件与保管人
Minter 泄漏不能治理；order/deposit replay protection；Admin 可 pause/rotate仍可构造虚假唯一 mint；需要监控、限额、HSM/relayer policy
Custody backend/key 泄漏AES-GCM、HKDF、Compose secret、DB/runtime role separation完全控制 backend 可盗 reserve；生产应 HSM/MPC、多签 source custody
第三方 TBC API 欺骗raw/decode/block/UTXO/ancestor/script 多重核对不是独立 SPV；建议多节点 quorum 或恢复 V3 proof path
HyperEVM RPC 欺骗/故障固定 RPC、chain 998、重复读取 receipt/block/code/state单 provider 风险；建议多 RPC quorum
重复付款/重复 mintbegin slot、TXID recovery、DB unique outpoint、contract replay mappings用户仍可能链外手动多付；需 reconciliation/manual review
CSRF/IDORsame-origin、cookie session、CSRF、identity-scoped repositories仍需持续安全测试
Supply mismatch1:1 raw amount、source decimals immutable、exact deposit/lock checksescrow lock 不 burn，报告需区分 totalSupply 与 circulating supply

安全不变量

  1. 浏览器/请求不能选择任意 RPC、chain、source network 或后台 custody key。
  2. 一个 source outpoint 只能被一笔 deposit/release plan 使用。
  3. 钱包 hash 不是成功证明；必须验证 exact transaction、receipt、canonical block 与确认数。
  4. V1.5 Admin signer 与 Minter 必须是三个不同 EVM addresses。
  5. wrapped/escrow 初始 paused；激活必须两名 signer 对 exact unpause() 达成一致。
  6. 反向 payout 只能在 exact permanent lock verified 后签名与广播。
审计状态

项目明确为 Testnet learning system，Solidity、custody、TBC transaction verification 与 operational controls 均未完成独立生产级审计。不得直接宣称“黑客无法攻破”或“完全安全”。

术语

Canonical block

按固定来源当前最佳链确认的 block；交易仅有 confirmations 还不够，block hash/height 也要重新对应。

Custody

后端控制源链 reserve key 的托管模型；用户依赖 operator 正确验证与释放。

Raw amount

最小单位整数。TT decimals=2 时 1,500,000 TT 对应 raw 150,000,000。

Replay protection

防同一 order/deposit/redemption/outpoint 被重复结算的合约 mapping 与数据库唯一约束。

结论

V1.5 达成了用户要求的低 gas 与可操作 flow，并通过 2-of-2 Admin、独立 Minter、严格状态持久化和 exact transaction verification 改善 V1 风险；它仍应被准确描述为托管桥，而非无需信任的跨链证明系统。
